## Масштабирование баз данных

Опишем стратегии масштабирования

### Сервис ставок
* Нельзя использовать неактуальные ставки. Ставки могут меняться часто. Поэтому для кэша стоит использовать короткий TTL + инвалидация по событию. 
* Нужны read-реплики: сервис только читает данные и будет читать данные с реплик. Также важно, чтобы с момента внесения новых ставок, розыгрыш осуществляется строго по этим ставкам. Поэтому реплики должны быть синхронные.
* Хоть данные часто обновляются и часто читаются, их объём не велик, а шардирование усложнит работу с данными при проведении аукционов. Поэтому в данном случае не стоит шардировать базу.

### Сервис кампаний
* Испольует NoSQL БД (например, Mongo), тк структура кампаний может меняться и возможен различный набор параметров у разных кампаний.
* Кампании меняются не так часто, поэтому для Ad Server можно настроить для кэша средний TTL + инвалидацию по событию. 
* Нагрузка на запись небольшая, поэтому read-реплики не нужны.
* При большом количестве рекламодателей, кампании можно шардировать по владельцу (рекламодателю).

### Сервис статистики
* Использует OLAP БД (например, Clickhouse), тк нужно строить аналитику.
* Кэширование не нужно, сервис только пишет события. 
* Можно использовать встроенное шардирование при большом объёме данных. 

### Сервис аналитики
* Использует OLAP БД (например, Clickhouse), тк нужно строить аналитику.
* Кэширование не нужно, аналитика пересчитывается не часто, но важны актуальные данные.
* Можно использовать встроенное шардирование при большом объёме данных. 

### Сервис финансов
* Использует собственную (per-service) релиционную БД (например, Postgres), тк важны ACID транзакции.
* Кэширование не нужно, тк примерно одинаково операций на запись и чтение.
* Read-реплики нужны, тк большой объём операций на чтение и запись. Лучше разграничить.
* Большой объём операций на чтение и запись, поэтому лучше шардировать базу. Шардировать можно по клиентам.
