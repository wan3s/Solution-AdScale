## Проектирование взаимодействие

* Для внутреннего взаимодействия лучше выбрать grpc. Размер информации о ставке небольшой. Если гонять через REST, то будет много накладных расходов на заголовки. Так же необходимо добавить повторные попытки для внутреннего взаимодействия. 
* Для внешнего взаимодействия лучше выбрать REST. С таким API проще интегрироваться + гибкость в выборе стека.
* Так как ставки могут быстро меняться, то здесь лучше использовать синхронный подход.
* Для асинхронного взаимодействия (отправка статистики или обновление кэшей) лучше использовать Kafka,  тк это более надёжный механизм: можно перечитать сообщения заново, можно подсадить нескольких потребителей. Информация о событиях кликов и показов критична, нельзя что-то потерять - по этим данным происходят финансовые расчеты с рекламодателями и DSP.
* API Gateway нужен в виде proxy. Нужен рейт лимитинг и circuit breaker.

| Взаимодействие | Circuit breaker | Retry | Кэш | Идемпотентость |
| --- | --- | --- | --- | --- |
| API Gateway -> Ad Server | Размыкаем для некоторых DSP | Нет | Нет | Нет |
| Ad Server -> Auction Engine | Нет | Retry с фиксированной задержкой, тк важен быстрый отклик | Кэш кампаний |  Нет |
| Advertiser Dashboard -> Financial Service | Нет | Retry с exponential backoff + jitter | Нет | Есть, чтобы не списать несколько раз одно и то же |
