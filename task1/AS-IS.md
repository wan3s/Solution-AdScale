### Узкие места и точки отказа

1. Единая БД - самое очевидное узкое место и точка отказа. В базу ходят Ad Server, Auction Engine - критичные для всего приложения контейнеры. Аналитики, выполняя тяжелые аналитические запросы, могут нагрузить базу довольно сильно. Настолько, что это будет негативно влиять критический путь. Это грозит финансовыми потерями и штрафами от DSP-партнёра.

2. Auction Engine - стоит на критическом пути определения победителя аукциона. Ставки меняются не так часто, их можно кешировать. Можно кешировать посчитанные веса для кандидатов: при последующих запросах Ad Server контейнер Auction Engine достанет из кеша посчитанные веса для кандидатов (если для каких-то кандидатов нет посчитанных весов в кеше, то посчитает) и выдаст победителя.

3. Delivery Service синхронно вызывает Statistics Service. Если Statistics Service не сможет успешно записать информацию о кликах и показах, то пользователь не увидит баннер. Статистику можно слать асинхронно через очередь сообщений.

4. Нет ретраев - в случае каких-то единичных сбоев клиент не увидит баннер, DSP-партнеру придется заново зарпашивать ответ по ставкам и проходить весь синхронный путь.

### Архитектурные проблемы, препятствующие масштабированию

1. Самая очевидная - монолит. Есть набор сервисов, которые стоят на критическом пути (Ad Server, Auction Engine, Delivery Service). Их можно вынести в отдельные контейнеры (микросервисы), что позволит их масштабировать. Тогда получится подготовиться к кратному росту нагрузки к концу года.

2. Одна БД без read-реплик, которая используется для всего. Её отказ полностью положит всё приложение. Как минимум можно добавить read-реплики для ставок, с которых будет читать Auction Engine, и read реплики для кампаний, которые будет читать Ad Server. Для аналитики информацию о кликах можно асинхронно выгружать в Clickhouse.

3. Нет асинхронного взаимодействия. При масштабировании контейнера может вырасти нагрузка на вызываемые контейнеры. Если вызываем контейнер не стоит на критическом пути и приемлима задержка, то вызываемый контейнер может асинхронно слушать сообщения от первого сервиса и обрабатывать их с адекватной для него скоростью. При синхронном взаимодействии пришлост бы масштабировать оба контейнера.


### Влияние текущей архитектуры на время отклика

1 запрос от DSP партнёра требует 3 похода в базу данных. По цепочке: выбираем кандидатов -> взвешиваем ставки и выбираем победителя -> формируем баннер -> делаем запись кликов и показов. Для DSP-партнера не нужно формарование баннера, а также записи в сервис статистики.
